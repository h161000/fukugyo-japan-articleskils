# 副業JAPAN文章・証拠画像・画像キャプションルール

副業JAPANの記事で、同梱`seo-site-skills`に対して追加適用するサイト固有の出力ルール。調査事実や記事全体の見出し順を変更せず、公開MDXの文章表現・証拠画像・画像キャプション・結論と締めの完成条件を定める。

## 記事内の証拠画像は赤枠のみ

記事内の証拠画像は、必要な箇所を切り出し、赤枠だけで強調する。LP、料金、特商法、会社情報、実績、口コミ、LINEや申込み後の資料など、記事本文の根拠として採用する画像全件に適用する。

- 制作側で見出し帯、番号バッジ、説明文、矢印などを画像へ追加しない。画像の内側・外側の帯のどちらにも焼き込まない。
- 元資料に含まれる文字、番号、見出し、ロゴは保持する。追加注釈と混同して削除・書き換えない。従来の個人情報の除外・マスキングは維持する。
- 赤枠は本文の根拠となる文や行を囲み、文字に重ねない。色は同梱article-evidence-image-captureの赤（`#e60012`）を使い、背景に応じた別色への変更や番号による区別は行わない。
- 説明は記事本文と画像直下のキャプションに記載する。出典・取得日・加工範囲は従来どおり画像対応表へ残す。
- 同梱writing-agentの「画像注釈（見出し帯＋番号＋注釈文）」の必須規定と`annotate_shot.py`の注釈追加処理は適用しない。証拠箇所の取得・切り出し・赤枠・WebP化は、同梱article-evidence-image-captureを使用する。
- アイキャッチ、フジの顔画像、共通LINE CTA画像は対象外とし、それぞれの専用仕様を使う。

画像完成時と納品前に、採用する証拠画像を全件目視する。赤枠が根拠箇所を指し、制作側の追加の帯・番号・説明文・矢印がないこと、元資料の内容と本文が一致することを確認する。画像対応表と`review-report.md`へ対象ファイルと判定を残し、追加注釈が残る画像は差し替えてから完了にする。寸法・容量の機械検査だけで、この目視確認を代替しない。

## 画像キャプション

本文のMarkdown画像には、直後へ内容を説明するキャプションを1つ置く。

```mdx
![画像に写っている内容を具体的に表すalt](/images/slug-section.webp)

<p style="font-size: 0.75em; color: #666; text-align: center; line-height: 1.5; margin-top: 6px;">画像から直接確認できる事実を簡潔に書きます。</p>
```

- 文字サイズは`0.75em`、文字色は`#666`、中央寄せ、行間は`1.5`、上余白は`6px`で統一する。
- キャプションには画像から直接確認できる事実だけを書き、推測や評価を混ぜない。
- 公開キャプションには`（ユーザー提供画像、YYYY-MM-DD確認）`や`（YYYY-MM-DD確認）`などの出典種別・確認日を付けない。
- 出典URL、ユーザー提供の別、取得日・確認日は削除せず、`images/evidence-webp/README.md`、`research_notes.json`、`facts.md`、`review-report.md`の該当箇所へ残す。
- アイキャッチはfrontmatterから表示するため、本文画像用キャプションの対象外とする。

## 文脈に合う表現

次の表現は使わず、同じ文脈では右側の表現を使う。

| 使用しない表現 | 使用する表現 |
|---|---|
| 一緒に整理できます | 相談案内では「相談できます」。実際の共同確認を説明するときは、その内容を具体的に書く |
| 口コミは次の3種類に分けて見ます | 調査済みなら「調べて分かった口コミの内容をお伝えします」など、結果を伝える表現にする |
| 流れを整理すると、次の順番です | 実際の案内を時系列で並べると、次のとおりです |
| LINEで流しています | LINEで共有しています |

副業情報や実際に続けている副業の話をLINEで届ける説明でも、「そのまま流しています」ではなく「共有しています」と書く。

表現を機械的に差し替えて前後が不自然になる場合は、意味を保った自然な文へ書き直す。読者が確認できる範囲を超えて、専門判断や対応能力を約束しない。

## 判断・調査結果・相談案内を明確にする

以下は副業JAPANの筆者の説明・判断・提案に適用する。例文を記事ごとの固定テンプレートにはしない。

| 観点 | 判断基準 | 修正例 |
|---|---|---|
| 現在の判断 | 確認した事実を理由に、現在の判断を言い切る。条件が整えば勧めると確認したわけではないのに「〜できるまでは」「〜できないうちは」で判断を先送りしない | 「費用と支援を比較できるまでは見送ります」→「費用と支援を比較できないので見送ります」 |
| 調査結果 | 調査済みの記事では「この記事では〜確認します」「次は〜見ておきます」など、これから調査するような予告を避け、読者が得られる結果を伝える | 「この記事では料金を確認します」→「この記事では、調べて分かった料金の条件をお伝えします」 |
| 提案の完結 | 必要な確認・行動を「〜したいところ」「〜しておきたいです」「〜も欲しいところ」で曖昧に終えない。必要性または取る行動を明示する | 「期間や内容も比べたいところ」→「期間や内容も含めて比較する必要があります」 |
| 直接的な相談案内 | 相談できる内容とLINEという相談先を伝える。「一緒に確認できます」「一緒に考えます」だけで相談案内を代替しない | 「私のLINEでも一緒に確認できます」→「私のLINEで相談できます」。相談内容は前後で具体化する |
| 具体例と文脈 | 「Aなのか、Bなのか。」で比較の説明を投げ出さず、違いを理解できる具体例として完結させる。次の段落が比較・評価・行動のどれを伝えるかに合わせる | 「テンプレートを渡すだけの支援もあれば、投稿の改善点まで教える支援もあります」→「同じサポートでも、中身は違いますよね」→「期間や回数は書面で説明を受けましょう」 |

### 意味を変えずに適用する範囲

- 「私なら → 確認した理由 → 判断」の順を維持する。未確認の料金や成果を確定した事実に変えて、言い切りを作らない。
- 「現在の資料では確認できない」「条件によって異なる」「本人の契約内容による」など、事実上必要な留保や仮定は残す。「〜ので」への一括置換はしない。
- 読者の「始めたい」という気持ち、自然な問いかけ、事実を短く示す体言止めは一律に禁止しない。読者に確認を促す「契約前に確認してください」も調査の予告とは別。
- 引用した広告・利用者の発言は書き換えない。一般的な支援の比較例を、その案件に実在するプランの説明として書かない。具体例には「たとえば」等を添え、前後から一般例と分かるようにする。
- 相談案内の具体性を保ちつつ、解決・返金・収益や専門判断を約束しない。共同確認の実際の方法を説明する文まで、機械的に「相談できます」へ置換しない。
- 同梱human-voiceの親しみや体言止めの指針と調整し、上の対象となる判断・提案は言い切る。語尾をすべて同じにそろえることを目的にしない。

## 導入の疑問と後続文

筆者が読者の気持ちを代弁して作る疑問文は、カギ括弧内でも筆者の文章として文脈を確認する。引用した広告・利用者の実際の発言と区別し、実際の引用文を都合よく書き換えない。

- 記事が想定する読者状態を、選定済みKW・案内内容と照合する。すでに登録・無料体験・購入・利益獲得を済ませた読者と、根拠なく決めつけない。裏付けのある読者状態や自然な仮定は一律禁止しない。
- 疑問は、仕組み・仕事内容・費用など記事が実際に答える内容にする。後続文がその疑問へ答えるか、回答に必要な説明へ自然に進むか確認する。
- 疑問文と後続文をセットで示し、前提が妥当な理由と、後続文が加える情報を説明する。「具体的」「自然」だけの判定は不可。

今回の修正例（文面を他案件へ固定流用しない）:

- 修正前：「無料体験で資金が増えたなら、月額費用を払っても続ける価値があるのかな？」
- 修正後：「AIFAって、どんな仕組みでお金が増えるの？　始めるのに費用はかかるのかな？」
- 判断理由：案件の仕組みや費用をまだ知らない読者に対して、体験後の継続判断へ話題が飛んでいた。修正後は仕組みと費用への疑問として、その後のサービス説明につなぐ。実際の後続文との対応も原稿ごとに確認する。

## 第三者レビューサイトの表記

副業案件を評価する第三者レビューサイトは、公開原稿では実名を出さず「第三者サイト」「別の第三者サイト」と表記する。ジョブネットワークセンター・副レポも対象。本文・見出し・吹き出し・出典表記・画像alt・キャプションを確認する。公的機関、案件の運営会社、公式サービスの名称へは適用しない。

- 修正前：レビューサイト「ジョブネットワークセンター」には、購入者と名乗る投稿もありました。
- 修正後：第三者サイトには、購入者と名乗る投稿もありました。
- 修正前：副レポにも同じ内容が掲載されていました。
- 修正後：同じ内容は、別の第三者サイトの記事にも転載されていました。

出典の実名・URL・取得日・投稿日時・転載関係は`facts.md`、`research_notes.json`等の調査記録に残す。一般化しても、販売側の発信、利用者の自己申告、第三者の評価の区別と、主張の未検証部分を明記する。同一投稿の転載を複数人の体験として数えない。

引用本文にサイト名がある場合は、引用を無断改変せず、必要な範囲の引用または引用符を付けない要約へ切り替え、元の発言は調査記録に保持する。画像に写る名称は証拠画像そのものの改変理由にしない。ここでの表記ルールは外部リンクを一括削除する指示ではなく、リンクは既存の出典規則とユーザーの個別指示に従う。

## 文章表現の横断レビュー

執筆後、独立criticに渡す前に記事全体を確認する。独立criticの1周でも既存5観点と、導入の前提・後続文の接続・第三者サイト表記の追加3観点を確認させ、主担当は指摘反映後の最終原稿で再確認する。

対象は導入・見出し・本文・吹き出し・相談案内・締め。検査候補が0件でも、言い換えや文脈の不自然さは全文を読んで確認する。単なる「問題なし」ではなく、該当文と理由を記録する。

ユーザーから一文の修正を指示された場合は、その意図に当たる表現が同じ記事のほかの箇所にもないか確認する。変更箇所の前後2段落、関連する吹き出し、導入なら導入全体を読み直し、重複・話題の飛躍・事実の変化がないことを確認する。ユーザーが修正範囲を限定した場合はその指定を優先する。他の記事やスキルの修正・公開まで承認されたとは扱わない。

### 検出と判定の記録

`check_fukugyojapan_editorial.py`は、5観点の見直し候補を元の行番号・前後の文章とともに出す。装飾タグを除いて表示文を検査し、コード・引用ブロック・引用された発言自体は候補抽出から除く。機械抽出は網羅性や文脈判断を保証しない。候補を自動置換しない。

既知の第三者レビューサイト名は公開原稿の検査でFAILにする。未知のサイト名も`source-naming`の意味確認で点検する。調査記録は検査による置換対象にしない。

最終原稿に対して、未判定の雛形を作る。

```bash
python3 <SKILL_ROOT>/scripts/check_fukugyojapan_editorial.py \
  <ARTICLEWORK>/article-draft.mdx <SITE_ROOT> \
  --review-output <ARTICLEWORK>/editorial-review.json
```

雛形生成直後は未確認なので終了コード1になる。既存のレビューは上書きしない。改稿時は別名に雛形を生成し、旧記録と照合して再確認した後で`editorial-review.json`を置き換える。

記録の埋め方:

現行の雛形は`schema_version: 2`。旧形式は次回レビュー時に新しい雛形を生成し、追加観点を確認する。バージョンやハッシュだけを書き換えて過去の判定を流用しない。

- `article_sha256`と`rules_sha256`は生成時の値を使う。本文やルールが変わったら再走査・再確認し、ハッシュだけを付け替えない。
- 最終原稿に残る候補は`candidates`に保持し、文脈上妥当な場合だけ`decision: "retain"`と具体的な`reason`を記録する。候補を消して判定済みに見せない。
- 修正して解消した候補は`changes`へ`before`・`after`・`reason`を記録する。`after`は現行原稿に存在する文を使う。残る候補に「修正済み」と書くだけでは合格にならない。
- `full_text_review.scopes`へ実際に確認した`intro`・`headings`・`body`・`balloons`・`consultation`・`closing`を記録する。
- `full_text_review.checks`の既存5観点（`judgment`・`results`・`recommendation`・`consultation`・`example-context`）に加え、`intro-premise`・`intro-connection`・`source-naming`を記録する。該当文と判断理由を`detail`へ書き、確認したものだけ`status: "pass"`にする。候補0件だけを理由に合格にしない。
- `intro_context`には、最初のH2より前の導入の表示文を行番号付きで自動収録する。カギ括弧・引用・吹き出しも含む。生成された文を削除・差し替えず、現行原稿と照合する。
- `intro-premise`には実際の疑問文を示し、筆者が作った問いか実際の引用か、想定読者と体験・利益等の前提が妥当かを記録する。`intro-connection`には疑問文と後続文を併記し、話題のつながりと新しく加わる情報を記録する。疑問文がない場合も、導入の該当文を示して前提と接続を確認する。
- `source-naming`には第三者サイトの公開表記と調査記録の保存先を示す。第三者レビューサイトを使わない記事では、そのことと実際の出典種別を具体的に記録する。

記入後に検証する。

```bash
python3 <SKILL_ROOT>/scripts/check_fukugyojapan_editorial.py \
  <ARTICLEWORK>/article-draft.mdx <SITE_ROOT> \
  --review <ARTICLEWORK>/editorial-review.json
```

`review-report.md`には変更の要点、残した表現の理由、前後の接続、根拠への影響を記録する。`workflow-state.json`の`wording-review`の証跡は`editorial-review.json`を指定する。workflow Gateは最終原稿とルールのハッシュ、現在の候補との一致、未判定候補、既存5観点と追加3観点、導入全文と全範囲の確認記録を照合する。未確認のまま納品完了にしない。形式上の合格は意味判断の正しさを保証しない。

## 筆者の判断を伝える文の組み立て

参加・契約を見送る判断では、文末に「私は見送ります」を後付けせず、「私なら」を先に置き、理由から判断へ自然につなげる。

- NG：高柳大輔のLIGHTNINGは、参加費を払って任せられる範囲が分かりにくく、私は見送ります。
- OK：私なら、高柳大輔のLIGHTNINGは参加費を払って任せられる範囲が分かりにくいので見送ります。

導入・結論・本文・まとめを横断して確認し、同様の表現にも適用する。ただし、すべての意見文を機械的に「私なら」で始めない。事実説明や見出しには適用しない。

## LP・LINE資料の取得者と本文での書き方

ユーザーが「フジが実際に登録して得た情報」と確認したLP情報・LINE画像は、フジ自身の調査・登録後の情報として本文に使用する。

制作担当がユーザーからファイルを受け取ったことを理由に、本文を「第三者から提供された画面の紹介」へ変更しない。

- NG：私自身が登録した体験ではなく、調査用に提供された画面を確認しています。
- OK：私がLINEに登録すると、3本の動画を見た人に参加方法を案内する流れでした。

資料の取得者が未確認の場合は、フジの登録体験と決めつけない。登録の確認だけで、購入・運用・出金・動画視聴まで経験したと書かない。登録日時や資料にないやり取りも補わない。

`facts.md`、`research_notes.json`、画像対応表には、「フジが取得した資料であること」と「ユーザーから制作担当へ提供されたこと」を分けて残す。ユーザーが確認した範囲と出典URL・取得日または不明であることも保持する。

## 装飾の原稿・表示確認

同梱`docs/design-guide.md`の「装飾の適用確認」に従う（正確な参照先は`references/seo-site-skills/docs/design-guide.md`）。

副業JAPANのCSSにマーカーや青文字の設定があることと、記事MDXがそれを使用していることを別々に確認する。MDX内の`<mark>`、青文字のインライン指定または対応クラスを確認した後、375px表示で実際の色・結論の文字サイズ・読みやすさを確認し、結果を`review-report.md`へ記録する。サイト固有の色味を保ち、共通CSSを変えて未指定の原稿を一括装飾しない。

## 納品前Gate

サイトルートで次を実行する。

```bash
python3 /Users/hirototakada/.codex/skills/fukugyojapanarticle/scripts/check_fukugyojapan_editorial.py \
  src/content/articles/<slug>.mdx \
  --review <ARTICLEWORK>/editorial-review.json
```

FAILがあれば公開・commit・push前に修正し、再実行する。機械検査の通過だけで文章の自然さを保証したことにはせず、`critic`と375px表示でも確認する。

次の2項目は機械検査とは別に記事全体を読み、`review-report.md`へ該当文と判定を記録する。

- 判断文の語順：「私なら → 理由 → 判断」になっているか。同型の後付け表現を導入・結論・本文・まとめに残していないか。
- 資料取得者と一人称：ユーザーが確認した取得者と本文の主語が一致しているか。制作担当への提供経路を筆者の未登録と混同せず、確認されていない体験も補っていないか。


## 結論と締めの完成条件

ここでは記事全体のH2順を固定せず、最初の結論と最後のまとめに必要な内容を定める。

### 最初の結論

1. 案件に対する筆者の判断を示す。
2. 判断の具体的な理由を、AlertBox内のリストまたは箇条書きで一覧にする。
3. 各理由について、読者が何を判断できないのか、どんな負担や不確実性につながるのかを説明する。
4. その説明を済ませてから共感・相談案内へつなぐ。

理由は原則3点程度とし、確認した根拠の数に合わせる。3点に合わせて理由を創作・分割したり、同じ理由を言い換えて水増ししない。各項目は本文の調査結果に対応させ、未確認・記載なし・実際の被害を区別する。「情報が不明なのでおすすめしない」という一文や、証拠画像だけで理由の説明を代替しない。

例えば、認可番号が未記入なら「認可を照合できない」、費用が不明なら「必要額を見積もれない」と判断へのつながりを説明する。この例の理由を他案件へ流用しない。

### 最後のまとめ

本文で確認した主要な理由を箇条書きで短く振り返り、読者が取る判断を伝えてから、選定済みのLINE CTA型へつなぐ。前半の理由をそのまま長文で複製せず、本文を読んだ後の要約として書く。ここで新しい根拠や未確認の体験を追加しない。

証拠画像1枚と共感文だけで終えない。相談案内で記事のまとめを置き換えない。POINT ZERO等の既存記事は構造の参考にできるが、理由・文面・結論を固定テンプレートとして移植しない。

### 判定と証跡

`review-report.md`に、判断文、理由一覧、各理由に対応する本文の根拠、判断へのつながり、相談案内へ移る箇所を引用・特定して記録する。締めでは本文との一致と新しい主張の有無も確認する。

`conclusion-review`と`closing-review`は、一覧があるだけではpassにしない。根拠の対応・論理・相談案内との順序まで確認する。機械検査が行うのは最初・最後のH2内のリスト存在確認であり、意味の妥当性は独立criticと主担当が確認する。
